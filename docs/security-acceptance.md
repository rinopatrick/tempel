# Tempel v1 threat model and security acceptance

This records the decisions from [#8](https://github.com/rinopatrick/tempel/issues/8)
and [#21](https://github.com/rinopatrick/tempel/issues/21) in the
[production-readiness map](https://github.com/rinopatrick/tempel/issues/5).
It specifies the v1 boundary and launch gate, not changes to the app, schema, or API.
Use the [glossary](../GLOSSARY.md) for domain terms.

## Assets and actors

| Asset | Where it lives |
| --- | --- |
| **Secret** (plaintext) | In the sender's browser before encryption and the recipient's browser after decryption. |
| **Ciphertext and IV** | The sender's browser makes an AES-256-GCM envelope. The server stores the envelope and returns it once; the recipient decrypts it locally. |
| **Fragment Key** | A per-Secret key shared as the fragment in `/s/<id>#<key>`. It is never in a legitimate Tempel HTTP path, query, or API body. The full share link, including the fragment, is sensitive. |
| **ID** | A 22-character unpadded base64url encoding of 16 random bytes, generated by the server. It is visible in HTTP paths and is sufficient to request (and consume) the envelope; it is not the decryption key. |
| **State and expiry** | The server persists the expiry and lifecycle state. `Created → Viewable → Burned` or `Created → Expired`. `Viewable` is a transient reveal step, not a second redeemable state. `Burned` and `Expired` are terminal. |

| Actor | Role or capability |
| --- | --- |
| Sender | Enters the Secret, chooses the TTL, and gives the full share link to the recipient. |
| Recipient | Redeems the link and reads the decrypted Secret. Tempel does not authenticate their identity. |
| Passive network observer | Can see connection metadata but, with TLS, cannot read HTTP requests or responses in transit. |
| Active scanner | Can send requests, guess IDs, or attempt to redeem a known ID before the intended recipient. |
| Curious operator | Can see server-side metadata and, with file access, inspect stored envelopes, but has no Fragment Key from normal traffic or storage. |
| Attacker with compromised server storage | Can obtain envelopes and metadata from storage. A storage-only disclosure does not give them the plaintext or Fragment Key. |

## Trust boundaries

- **Browser:** Trust the browser and the Tempel code it runs to encrypt and decrypt locally and not leak the Secret or Fragment Key. Create sends only `{ ciphertext, iv, ttlSeconds }`; Reveal reads the fragment locally and fetches the envelope by ID. Browsers omit fragments from HTTP navigation, and Tempel does not add the key to API requests.
- **Server and vault:** Trust them for availability, expiry and atomic single redemption, not with the plaintext or key. An operator or attacker who can modify the served client code is outside the storage-only confidentiality claim. The endpoint rejects explicit top-level `key` and `plaintext` fields; validation cannot prove arbitrary strings sent by a third party are ciphertext.
- **Network and edge:** Do not trust the network. Assume TLS at the trusted proxy per [ADR-0001](adr/0001-deploy-target-and-release.md) and restrict direct access to the Node origin. The proxy must supply the real client IP and strip any client-supplied identity headers that the app trusts rather than forwarding them. The current limiter reads `CF-Connecting-IP`, `X-Vercel-Forwarded-For`, `X-Forwarded-For`, then `X-Real-IP`; overwriting only `X-Forwarded-For` is not sufficient if higher-priority headers reach the app. Do not cache reveal responses at the edge.

## Handled threats and evidence

| Threat | Required observable behavior | Existing test seam |
| --- | --- | --- |
| Plaintext or key reaches the API | The Composer submits only the envelope and TTL; Reveal obtains the envelope and decrypts locally. POST with a top-level `key` or `plaintext` returns `400 {"error":"key-rejected"}` without storing a Secret. | Browser [Composer](../src/app/composer.test.tsx) and [Reveal View](../src/app/s/reveal-view.test.tsx); client request [creation](../src/secret/composer.test.ts) and [reveal](../src/secret/reveal.test.ts); [POST route](../src/app/api/secrets/route.test.ts). |
| Fragment Key leaks through a request or stored envelope | The full link contains the key only after `#`; the Reveal fetch URL contains only the ID. The key is separate from the stored envelope, the fragment parser rejects malformed keys, and a different key cannot decrypt the envelope. | [Share-link](../src/secret/share-link.test.ts), [reveal request](../src/secret/reveal.test.ts), and [crypto](../src/secret/crypto.test.ts) tests. Fragment omission on navigation is a browser URL property, not something the HTTP route enforces. |
| Repeat or concurrent Reveal returns the envelope twice | One winner gets `200` with `{ ciphertext, iv }`. The SQLite vault commits the Burn before returning the envelope. Later or losing requests get `410 {"error":"gone","reason":"burned"}` with no envelope. | [Persistent HTTP routes](../src/app/api/secrets/persistent-route.test.ts) for repeated and racing requests; [persistent vault](../src/secret/vault-persistent.test.ts) for races across workers on one file. |
| An expired Secret is revealed | TTL is 1, 6, or 24 hours (1 hour by default if omitted). At expiry, Reveal or a status check lazily clears the envelope and sets `Expired`, with no sweeper. Even after restart, Reveal gets `410 {"error":"gone","reason":"expired"}` with no envelope. | [GET route](../src/app/api/secrets/%5Bid%5D/route.test.ts), [persistent HTTP routes](../src/app/api/secrets/persistent-route.test.ts), and [persistent vault](../src/secret/vault-persistent.test.ts), including expiry between read and Burn. |
| Enumeration or request floods load the vault | Independent per-IP limits for create and reveal apply before vault access. Within the one-minute window, the 11th POST or 61st GET gets `429 {"error":"rate-limited"}` with `Retry-After` in seconds, without a store or reveal call for the rejected request. | [POST route](../src/app/api/secrets/route.test.ts) and [GET route](../src/app/api/secrets/%5Bid%5D/route.test.ts); [limiter windows and IP buckets](../src/secret/rate-limit.test.ts). |
| Malformed ID triggers a vault query or is confused with a missing Secret | Within the rate limit, an ID outside the 22-character URL-safe format gets `404 {"error":"unknown"}`, without a reveal or gone-reason lookup. An ID of valid shape that was never stored gets `410 {"error":"gone","reason":"unknown"}`. | [GET route](../src/app/api/secrets/%5Bid%5D/route.test.ts) for malformed IDs and no lookup; [persistent HTTP routes](../src/app/api/secrets/persistent-route.test.ts) for valid-shape unknown IDs. |

## Accepted risks and exclusions

- A database reader can see Ciphertext, IVs, and metadata. Lazy expiry only clears the live envelope on access, and clearing a row is not secure erasure of the database file, WAL, or backups. Confidentiality still depends on keeping the Fragment Key separate.
- There is no recipient authentication. A leaked link can be redeemed first, and even an ID without the key can consume its envelope. Atomic Burn prevents multiple successful downloads, not unauthorized first use. A dropped response can consume the link without delivering the Secret; a recipient can also keep a copy.
- Shared NATs share one IP budget and can hit false positives. The per-route constants are tunable; the limiter is not a global DDoS defense. Its in-process counters reset on restart. Distributed rate-limit state is outside v1.
- Compromised endpoints (including browsers, extensions, or actively modified application code) and exposure of the full link through the sharing channel, clipboard, or browser history (including synced history) are outside the model.
- A file-init failure falls back to the in-memory vault, which loses Secrets and Burned/Expired state on restart. This is not acceptable in production; prove the file vault is in use before launch.
- The seed route is for isolated verification only. If enabled on a public instance, it permits unauthorized writes that can destroy existing Secrets without revealing them.
- Deployment target selection belongs to [ADR-0001](adr/0001-deploy-target-and-release.md); the [visual UI gate](qa/ui-state-gate.md) is separate. Multi-recipient sharing and server key rotation are out of scope; v1 holds no server-side Secret decryption key.

## Launch gate

Do not mark the security gate green until every item passes on the release candidate:

- [ ] Use a patched Node 22 release (at least 22.13) for local checks and on the release host; record `node --version`. Install pinned dependencies with `npm ci`. Run `npm test -- --run` and `npx tsc --noEmit`; both exit successfully.
- [ ] Run `npm run build`; it succeeds and lists both `/api/secrets` and `/api/secrets/[id]`.
- [ ] Start the built app with `npm start`, a fresh isolated SQLite file (`TEMPEL_DB_PATH`, `TEMPEL_STORE` unset), and `TEMPEL_PROBE_SEED=1` **on the isolated pre-release instance only**. From the same host, run `node scripts/live-probe.mjs http://localhost:3111` (use the actual `PORT`, e.g. `3111`). Run this probe against the test instance directly, not through a public proxy; it uses a fixture IP header to isolate its flood budget.
  - Create returns `201`; first Reveal returns `200` with the envelope; the next returns `410` with reason `burned`.
  - The past-expiry fixture returns `410` with reason `expired`.
  - The over-budget POST returns `429` with `Retry-After`.
  - All probe assertions pass, including health, malformed and unknown IDs, and key rejection. The script exits zero with `LIVE PROBE GREEN`.
- [ ] Prove the probe used SQLite: the app log contains no `[tempel] file store unavailable` warning, and the fresh file at `TEMPEL_DB_PATH` contains both `burned` and `expired` rows. Check the file read-only with a SQLite client:

  ```sql
  SELECT state, count(*) FROM secrets
  WHERE state IN ('burned', 'expired') GROUP BY state;
  ```

  Both states must have a nonzero count. The HTTP probe also passes in memory mode, so its success alone is not evidence of persistence.
- [ ] Verify the deployment edge before public traffic. The URL serves valid HTTPS and the Node origin is not directly reachable. Inspect the proxy configuration and a test request at the origin: `X-Forwarded-For` contains exactly the known client address, and the other three client-IP headers are stripped.
- [ ] On the release configuration with `TEMPEL_PROBE_SEED` unset or `0`, `POST /api/seed-expired` returns `404` through the edge. Create a disposable Secret, reveal it through the edge, and repeat the same GET: the first response is `200` and the second is `410 burned`, not a cached envelope. Verify the edge is configured to bypass caching on the Reveal API and the disposable Secret's `burned` row is in the configured production SQLite file.
